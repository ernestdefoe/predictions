# Predictions: working rules

- **Commit straight to `main` and push. Never open a pull request on this repo.** Commit subjects are conventional (`feat:`, `fix:`); the release drafter bumps from the subject.
- `js/dist` is committed and is what forums load. After any change under `js/src`, run `npm run build` in `js/` (from a fresh `npm ci`) and commit the bundle; CI fails if it is stale.
- Publishing a release is Ernest's click. Nothing is announced until he says so. Every change goes to the Command Center session for review before release.

## Design rules that exist for a reason

- **The API is resources** (2.x): `PredictionResource` (Index with `Listing` filters, Show, Create/Update/Delete through `Editor`, and `pick`/`unpick`/`settle` endpoints), `PickResource` (who picked what, read-only; scope() hides picks still hidden), `SeasonResource` (admin Create ends the season) and `StandingResource` (`prediction-standings`, the leaderboard: rows of `prediction_scores`, or all-time totals; rank, oracle and the members are added in its `after()` hook, since the serializer's loader needs a primary key that totals lack). No plain routes. JSON:API reserves `type`, so a prediction's kind is the `kind` attribute. Each input is a typed field with its own rules that sets the model; `Editor` then checks what depends on the whole row, from `getDirty()` read through the casts, `pendingLabels` (choices) and `lockNow`. The discussion is a `writableOnCreate` relationship.
- Errors are `Refusal`s (code + status), turned into `{errors: [{status, code}]}` by `Api\RefusalHandler` (Extend\ErrorHandling); the browser maps each code to a sentence (`forum.errors.*`), and a field rule's `validation_error` shows its `detail`. `call()` retries a write once on 409 `predictions_busy`.
- **Every write to a prediction runs under its `RowLock`** (a cache lock named after the row, taken with `get()`, never waiting: busy = Refusal `predictions_busy` 409), and inside it a transaction that re-reads the row `lockForUpdate()`. `lockForUpdate` alone is a no-op on SQLite. Seasons lock `season`.
- **Picks are judged by `lock_at`, under that lock** (`Picks::lockRow` re-reads and re-checks). Never accept a pick based on a copy of the prediction read before the transaction, and never depend on `locked_at` (the scheduler's stamp, used only for the "time to settle" alert).
- **Settling never scores in the request.** `Settler` writes the answer under the row lock, clears `scored_at` and queues `Job\ScorePrediction`. `Scorer` runs only while `scored_at` is null, under the row lock, and rebuilds every pick result and the touched members' season rows (`Scores::rebuild`) from scratch. `predictions:tick` (every minute) scores anything left unscored. Every step must stay idempotent.
- 🚨 **Whoever settles a prediction never scores from it** (`Scorer` nulls their pick, `Scores::rebuild` skips it): otherwise a member opens a yes/no, picks, settles it their way and farms points. Once others have picked, only a moderator can move the lock LATER (a creator could reopen picks after kickoff).
- 🚨 **A prediction counts toward the leaderboard only with `min_pickers` (setting, default 3) pickers besides the settler** (`counted` on the row, set by `Scorer`; `Scores::rebuild` reads only counted ones), and "closest" needs 2+ guesses: two accounts can't farm (A opens, B picks, A settles). Hits still show; points are null.
- **Settling:** the creator settles once (`canSettle`); corrections and voids are moderator-only (`canVoid`); nothing re-settles into an ENDED season. The policy's `settle` only asks who may settle at all; `Settler` re-checks the exact rule under the lock (so an ended season gets its own message). Lists pass the ended-season flag into `canSettle`/`canVoid` (one query per page, never per card).
- **Ownership needs `predictions.create`** (`isOwner`): a suspended member's groups are taken away, so they can't edit, settle or delete. Once others have picked, the title and hidden-picks switch are frozen except for moderators (`canEditWording`). "Others have picked" is always counted inside the lock, after `lockForUpdate` (`Editor::update`/`delete`).
- **Deleting a discussion deletes its predictions** (`Listener\Cleanup` on Deleting, with `Scores::rebuildFor`; the FK cascades too): a prediction left without its discussion would turn public. Deleting a member drops the counts they were in by one (bulk, atomic) and queues `Job\RefreshNumberStats` for closed number predictions.
- **Counts move by one per pick** (atomic increments under the RowLock); never recount on a pick. A number's `stats` are worked out once picks close: `predictions:tick` at the lock and `Scorer` at the settle, both through `Picks::refreshStats`/`Scoring::stats`. An open number shows no chart.
- Visibility is `Extend\ModelVisibility` (`Access\ScopePredictionVisibility`): use `whereVisibleTo`, never a local scope. Oracle group changes dispatch `GroupsChanged` for each member moved.
- **Oracle group:** only memberships this extension added are taken back (`prediction_awards.group_id` records them); Admins, Guests, Members and Moderators are never an Oracle group (`Seasons::NEVER_ORACLE_GROUPS`). The admin select stores `g5` (integer-like keys get re-sorted, dropping "No group" to the bottom); `Seasons` reads the digits.
- Points are written with one UPDATE per distinct result, never one per pick. Totals are recounted, never incremented.
- All-time standings (sums of every season row) are cached under `Scores::version()`, which every `Scores::rebuild`/`forgetMember` bumps: never write `prediction_scores` anywhere else, or the cached board goes stale.
- Who picked what (`prediction-picks`) is paged (100 at a time, "Show more"); per-choice counts come from the card's option counts, never from the rows loaded.
- A pick and an answer are checked by one rule, `Prediction::checkedAnswer`.
- The leaderboard reads `prediction_scores` only (one query, the members, one count for the first row's rank, the Oracles). Never sum picks at read time, and never call `Season::current()` on a GET (it can insert). The viewer's own row is a second request with `filter[user]`.
- Notification blueprints extend `Notification\PredictionBlueprint` and carry **no data**, so `sync()` matches the earlier alert and a correction or void takes it back. Their subject (`Prediction`) has the `predictions` API resource and the `predictions` store model: without either, notification lists break.
- `Api\Card` is the ONE definition of what a card shows beyond its columns (typed, readonly). `Presenter::many` builds a page of Cards in a fixed number of queries (options eager loaded, one query each for the viewer's picks, the "closest" faces and ended seasons). Each typed resource field reads one Card property through `Cards`: the getter queues its prediction and returns a closure, and the first closure lays out the whole page (WeakMap by request). Never hand-build attribute arrays again. Keep it that way; `the_list_costs_the_same_queries_for_one_card_or_twenty` proves it.
- Hidden picks: option counts, number stats and who-picked are left out on the server while `hide_picks` and the lock hasn't passed (`Prediction::picksVisible`). Someone else's picks list (`filter[user]`) only covers predictions whose picks are already visible.
- `predictionIds` on a discussion is only on the discussion Show endpoint; `predictionRecord` on a user only on the user Show endpoint. Never add per-item work to list endpoints.
- Frontend: routes, store models (`predictions`, `prediction-picks`) and notifications are declared in `js/src/forum/extend.ts` (Extend.Routes/Store/Notification), never assigned on `app`. forum.js only wires things up; everything else is ONE lazy chunk (`components/index.ts`). Two chunks sharing the card make webpack emit a shared chunk `jsDirectory` doesn't publish. `data.ts` pushes JSON:API answers into `app.store` and turns them into the plain objects cards read (`plain()`); an action's answer carries no relationships, so `plain()` only sets user/discussion when present.
- TypeScript with `flarum-tsconfig` (`npm run check-typings`); `m` and `flarum` are typed globals, never `declare`d. A catch that ends a request already alerted by `call()` says so in a comment.
- A prediction link becomes its card by SWAPPING the link once the card has loaded (`embedCard`): never insert extra nodes into a post body, whose top level belongs to m.trust (it removes by node count). Plain-text posts have no <p>, so links sit straight in `.Post-body`; the post's first node is never swapped.
- Cards inside posts are separate Mithril roots (`m.mount`, `components/mount.tsx`): a post's subtree retainer would otherwise never redraw them.
- Mithril has no function components: every component is a class.
- Composer chip: priority 1 in DiscussionComposer, -5 in ReplyComposer (the reply's title stays first), spaced to match FoF Polls' "Add Poll".
- Avatars: Flarum 2 sizes them with `--size`, and our fake user's `color()` needs the `#`.
- FoF Badges is touched only in `Award/BadgeAward.php`, bound to `Award\OracleBadge` by `BadgesServiceProvider`, which `Extend\Conditional` registers only while `fof-badges` is enabled (`NoOracleBadge` otherwise). The Oracle badge has no trigger, so FoF's recalculation never revokes it.
- `extend.php` uses string setting keys, never `Settings::` constants (reading our own classes while extend.php loads fatals every request mid-deploy). Every default lives in `Extend\Settings()->default()`, read without a fallback.

## Testing

- `composer test:setup && composer test` (integration), `composer analyse:phpstan`. Set DB_DRIVER (mysql/pgsql/sqlite) with `export` in a subshell and CONFIRM the "Connecting to …" line: without it setup silently uses SQLite. Never use the prefix `pg_` on PostgreSQL (`pg_settings` is a system view).
